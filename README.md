## 1. 실행 방법

### 사전 준비

| 항목 | 버전 |
|------|------|
| JDK | 21 이상 |
| MySQL | 8.x |
| Node.js | 18 이상 |

### 1) 저장소 클론

```bash
git clone https://github.com/jintheog/messengerApp.git
cd messengerApp
```

### 2) 데이터베이스 생성

MySQL에 접속해서 데이터베이스만 생성. 테이블 생성 불필요.

```sql
CREATE DATABASE messenger DEFAULT CHARACTER SET utf8mb4;
```
`utf8`는 이모지가 들어가면 저장 실패.

### 3) DB 접속 정보 수정

`backend/src/main/resources/application.properties`에서 아래 두 줄을
본인 MySQL 계정으로 바꿔주세요.

```properties
spring.datasource.username=root
spring.datasource.password=본인_비밀번호
```

데이터베이스 이름을 `messenger`가 아닌 다른 것으로 만들었다면
`spring.datasource.url`의 끝부분도 같이 바꿔야 합니다.

### 4) 백엔드 실행

```bash
cd backend
./gradlew bootRun
```

Windows PowerShell에서는 `.\gradlew.bat bootRun`.

### 5) 프론트엔드 실행

백엔드를 켜둔 상태로 터미널을 하나 더 열어주세요.

```bash
cd frontend
npm install
npm run dev
```

브라우저에서 `http://localhost:5173`으로 접속.

### 6) 동작 확인

저장소 루트의 `recipients_sample.csv`를 그대로 업로드.
데이터 40행이 이렇게 갈리는 것이 정상 동작입니다.

| 결과 | 건수 |
|------|------|
| 저장 | 32 |
| 파일 내 중복으로 건너뜀 | 2 |
| 거절 | 6 |
| 경고와 함께 저장 | 1 |

같은 파일을 한 번 더 올리면 저장 0건, "이미 등록된 번호" 32건.

### 7) 테스트 실행

```bash
cd backend
./gradlew test
```

CSV 파싱 테스트는 DB를 쓰지 않으므로 MySQL이 꺼져 있어도 돌아갑니다.

## 2. 데이터 모델 설명

### 구현한 테이블: `recipient`

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | bigint | PK, auto increment |
| name | varchar(50) | NOT NULL |
| phone | varchar(20) | NOT NULL, UNIQUE |
| grade | varchar(20) | NOT NULL, VIP / GOLD / GENERAL / UNKNOWN |
| created_at | datetime | NOT NULL |

**`phone`은 숫자만 남겨서 저장했습니다.** CSV에 하이픈, 공백, `+82`가 섞여
들어오는데 원본 형태로 저장하면 `012-2341-5678`과 `01223415678`이 서로 다른
데이터가 됩니다. 중복 판정과 조회가 전부 깨지므로 저장 시점에 형식을 통일하고,
화면에 보여줄 때 마스킹해서 내보냅니다.

**`phone`에 UNIQUE 제약을 걸었습니다.** 번호 중복은 애플리케이션에서 먼저
걸러내지만, 두 요청이 동시에 들어오면 각각 이미 없는 번호라고 둘 다
저장을 시도할 수 있습니다. 애플리케이션 검증은 사용자에게 사유를 알려주기 위한
것이고, DB 제약은 데이터가 깨지지 않게 하는 최종 안전망입니다.

**`grade`는 4개 값으로 정규화했습니다.** 샘플 파일에 `VIP`, `vip`, `V.I.P`,
`골드`, `GOLD`, `일반`, `GENERAL`, 빈 값이 섞여 있었습니다. 문자열 그대로
저장하면 필터 목록에 같은 등급이 여러 번 뜨고, VIP로 필터링했을 때 `vip`
데이터가 안 나옵니다. 해석할 수 없는 값은 `UNKNOWN`으로 두고 행은 살립니다.
이름과 번호가 멀쩡한데 등급 하나 때문에 버릴 이유가 없기 때문입니다.

**`created_at`은 요구사항에 없지만 넣었습니다.** 페이징 때문에 필요합니다.
정렬 기준이 없으면 DB가 행 순서를 보장하지 않아서, 1페이지에 나온 사람이
2페이지에 또 나오거나 아예 빠질 수 있습니다.

### 구현하지 못한 테이블

발송과 이력은 시간과 역량 부족으로 구현하지 못했습니다.

**구현하지 못한 테이블 설계 내용:**

**`message_request`** — 발송 요청 1건이 1행입니다.
메시지 내용, 대상 조건(`ALL` / `GRADES`), 요청 시각, 성공·실패 건수를 담습니다.
발송 이력 목록이 이 테이블 조회입니다.

**`message_request_grade`** — 요청 1건에 등급 N행이 붙는 테이블입니다.
이 테이블은 **발송 대상 등급을 여러 개 고를 수 있게 하려고 추가했습니다.**
그러면 `message_request`의 컬럼 하나로는 값을 담을 수 없습니다.
그래서 `(request_id, grade)`를 묶어 PK로 갖는 별도 테이블을 뒀습니다.
(이전에 제가 했던 도서관리 프로그램 어플에서도 회원별 등급을 비슷한 방법으로 관리 하였습니다.)

**`message_result`** — 수신자 1명당 1행으로 성공/실패를 기록합니다.
여기에는 `recipient_id`와 함께 **발송 당시의 이름과 번호를 복사해서
저장합니다.** 발송이력과 수신자를 조인만 걸어두면 수신자가 번호를 바꾸거나 삭제됐을 때 정확한 이력을 다시 조회 하기 어렵습니다.
e.g. 3개월 전에 A번호로 보냈는데 그 회원이 번호변경 후 지금 조회하면 B번호로 보낸 것처럼 보이는 경우.

## 3. 기술 선택 이유

### 백엔드

**Java 21 + Spring Boot 3.5.16**

과제 요구사항이 Spring Boot 3.x여서 3.x를 썼습니다. 다만 3.x 계열은
2026년 6월 30일에 오픈소스 지원이 끝났고 3.5.16이 마지막 release입니다.
Spring Initializr에도 더 이상 3.x가 나오지 않아서, 4.x로 생성한 뒤
플러그인 버전을 내려서 맞췄습니다.

**Gradle**

평소에 gradle로 프로젝트를 만들고 설정하는것에 더 익숙 하여 선택 하였습니다.

**JPA (MyBatis 대신)**

요구사항에 "등급 필터 + 페이징"이 있는데, JPA면 `Page<Recipient> findByGrade(Grade, Pageable)` 한 줄로
목록 쿼리와 전체 건수 쿼리가 같이 만들어집니다. MyBatis로 하면 목록 SQL과
count SQL을 따로 쓰거나 페이징 플러그인을 붙여야 합니다.

MyBatis가 유리한 구간은 복잡한 리포트성 쿼리나 튜닝이 중요한 대용량 조회인데
이 과제에는 해당하는 것이 없었습니다.

JPA의 취약점: MySQL의 auto increment를 쓰면 Hibernate가 배치 insert를 하지 못합니다. 샘플이 40행이라 문제가 없지만
CSV가 10만 행이면 `saveAll`이 매우 느려지고, 그때는 그 부분만 `JdbcTemplate`으로 분리 해야합니다.

**MySQL**

과제에서 자유 선택이라 익숙한 것을 골랐습니다.

**Apache Commons CSV**

처음에는 쉼표로 잘라서 직접 파싱하려고 했습니다. 그런데 AI가 샘플 파일을
먼저 훑어보고 문제가 될 행들을 정리해줬는데, 그중에 `"고, 은지"`가 있었습니다.
따옴표로 감싼 안쪽에 쉼표가 들어 있는 이름입니다.
확인해보니 `line.split(",")`으로는 이 행이 4개 컬럼으로 쪼개지고 이름이
`"고`가 됩니다. 그래서 따옴표를 제대로 처리하는 라이브러리가 필요하다고
판단해서 AI가 Apache Commons CSV를 골라 주었습니다. 헤더 처리와 빈 줄 무시도 같이 해결됩니다.

**Lombok**

엔티티의 getter와 생성자 코드를 줄이려고 썼습니다.
반대로 값을 담아 전달하기만 하는 DTO는 Lombok 대신 `record`로 만들었습니다.
`record`는 자바 표준 문법이라 라이브러리 없이 동작하고, 필드를 바꿀 수 없어서
"만들어진 뒤 변하지 않는 값" (CSV 파싱 결과)이라는 성격과 맞습니다.
엔티티는 JPA가 기본 생성자를 요구하고 필드에 값을 나중에 채워 넣는 방식이라
`record`로 만들 수 없어서 클래스 + Lombok으로 두었습니다.

### 프론트엔드 (100% AI)

**React + Vite, JavaScript**

과제 요구사항이 React 18 이상이였고 Vite로 설정없이 바로 실행 하는 방법을 알아서 선택 하였습니다. 

**상태관리 라이브러리 없음**

정확한 이해도가 없는 Redux 같은 것을 넣지 않았습니다. 

**라우터 없음**

한 페이지에 섹션을 나열하는 구조로 만들었습니다.

프론트에 들어가는 내용은 전부 100% AI에 일임 하였습니다. 

## 4. 애매했던 요구사항과 내가 내린 가정

요구사항은 CSV 형식을 `이름, 휴대폰번호, 고객등급`이라고만 알려주는데
샘플 파일에는 정상적이지 않은 행이 여러 개 섞여 있었습니다.
일관적이지 않은 데이터 세트를 처리 해야 할때 어떤 행을 저장하고 어떤 행을 부적합하다고 판단하고 저장목록에서 제외 할지를 먼저 정해야 했습니다.

이 앱은 결국 문자를 발송하고, 잘못된 번호로 나간 문자는 취소할 수 없습니다.
그래서 **되돌릴 수 없는 부작용이 있는 동작 (잘못된 번호로 문자 발송 혹은 수신이 불가능한 번호로 문자 발송)은 애초에 실행 하지 않는다**고 생각 하였을때 발신이 되지 않을 번호 (e.g. 맨 앞 0이 절삭됨)는 애초에 목록에 저장 하지 않고 문자를 전송 하는 비용도 쓰지 않도록 했습니다.


### 4-1. 문자 수신 가능한 번호 파악

번호 형식 규정이 없습니다. 샘플에는 하이픈, 공백, `+82`, 앞뒤 공백,
자릿수 부족·초과가 모두 들어 있습니다.

이 순서로 정규화하고, 통과하지 못하면 거절합니다.

1. 앞뒤 공백 제거
2. `+82` → `0` 치환
3. 하이픈·공백 제거
4. 남은 값이 전부 숫자인지 확인
5. 앞자리 0 누락 의심 건을 별도 사유로 거절 (4-2)
6. 10~11자리인지 확인
7. `01`로 시작하는지 확인

4번이 6번보다 먼저인 것이 중요합니다. `012-abc-1234`는 하이픈만 지우면
10글자가 되어 자릿수 검사를 그냥 통과합니다.

**`01`로 시작하는지를 검사합니다.** 자릿수만 보면 `02-1234-5678`이
`0212345678`, 10자리이고 `0`으로 시작해서 통과해버립니다. 유선번호는 문자를
받을 수 없으니 저장해도 발송이 실패할 뿐입니다. 그런데 `012`도 `01`로
시작하므로, 이 조건은 샘플을 하나도 죽이지 않으면서 유선번호를 걸러냅니다.

`02`와 `03`만 막는 방법도 생각했지만 `041`, `051` 같은 다른 지역번호와
`070`(인터넷전화)이 남습니다. `01` 접두어 조건이 한 번에 다 막습니다.

남은 한계는 `012`처럼 실제로 존재하지 않는 앞자리가 통과한다는 점입니다.
실제 서비스라면 통신사 앞자리 목록을 확인해서 `010`, `011`, `016`, `017`,
`018`, `019`로 좁혀야 합니다.

### 4-2. 앞자리 0이 빠진 것 같은 번호

29행이 `1012345678`입니다. 엑셀이 앞자리 0을 지운 결과로 보이고,
0을 붙이면 유효한 번호가 됩니다.

**복원하지 않고 거절했습니다.** 추측이 맞으면 편하지만 틀리면 전혀 모르는
제3자에게 문자가 갑니다. `1012345678`이 원래 `01012345678`이었다는 보장이
없습니다.

대신 자릿수 오류로 전달 하지 않고 사유를 따로 만들었습니다.
`"앞자리 0이 누락된 것으로 보입니다 (원본 확인 필요)"`
`"자릿수가 맞지 않습니다"`라고만 하면 담당자는 10자리를 세보고
"맞는데 왜?"라며 원인을 못 찾습니다. 사람이 원본을 보면 해결되는
문제이므로 판단을 사람에게 넘겼습니다.

### 4-3. 고객등급의 값 종류

어떤 값이 올 수 있는지 정의가 없고, 샘플에 `VIP`, `vip`, `V.I.P`, `GOLD`,
`골드`, `일반`, `GENERAL`, 빈 값이 섞여 있습니다.

`VIP` / `GOLD` / `GENERAL` / `UNKNOWN` 4개로 정규화했습니다.
대문자로 바꾸고 영숫자·한글이 아닌 문자를 제거합니다.

문자열 그대로 저장하면 화면 필터 목록에 같은 등급이 세 번 뜨고,
`VIP`로 필터링했을 때 `vip` 데이터가 안 나오는 버그가 됩니다.

**`골드`=`GOLD`, `일반`=`GENERAL` 매핑은 제 짐작입니다.** 

### 4-4. 어떤 항목이 필수인가

세 컬럼 중 무엇이 없으면 저장하면 안 되는지 적혀 있지 않습니다.
기준을 하나 세웠습니다. **"그 값이 없으면 데이터가 존재 의미를 잃는가."**

| 없는 값 | 처리 | 이유 |
|---|---|---|
| 휴대폰번호 | 거절 | 발송 자체가 불가능 |
| 이름 | 거절 | 담당자가 발송 대상을 검토할 수 없음 |
| 고객등급 | `UNKNOWN` 저장 + 경고 | 발송과 식별에 지장 없음 |

이름 없는 행은 번호가 유효해서 발송은 가능하지만, 담당자가 "이 사람에게
보내도 되는가"를 판단할 수 없습니다. 이 앱은 관리 도구이고 담당자의 검토가
핵심 기능이라고 봤습니다.

등급 없는 행을 살린 이유는 이름과 번호가 멀쩡한데 등급 하나 때문에 그 사람의 번호를 저장 목록에서
누락 시키면 그 사람은 목록에 아예 없어서 안내를 못 받기 때문입니다. 

### 4-5. 중복의 정의

무엇을 기준으로 중복인지, 어느 행을 살릴지 규정이 없습니다.

**번호 기준**으로 판정합니다. 이름은 동명이인이 있을 수 있고 번호가 사람을
식별하는 값입니다. **먼저 온 행을 유지**하고 나중 행을 버립니다.

어느 쪽이 최신 정보인지 알 방법이 없습니다. "같은 번호로 두 번
보내는 것보다 한 번이 안전하다"는 기준으로 정하고, 어느 행을 건너뛰었는지
행 번호로 알려줍니다.

**"파일 내 중복"과 "이미 등록된 번호"는 구분해서 보고합니다.**
담당자가 해야 할 행동이 다릅니다. 앞은 원본 파일을 정리해야 하고,
뒤는 아무것도 안 해도 되는 정상 상황입니다. 합쳐서 "실패 34건"이라고
알려주면 정상 데이터를 다시 올리려고 헛수고를 합니다.

### 4-6. 문제 있는 행이 섞여 있을 때 전체를 실패시킬 것인가

**부분 저장입니다.** 40행 중 8행이 문제여도 32행은 저장됩니다.

요구사항이 샘플 파일을 "그대로 업로드했을 때 동작해야 한다"고 했습니다

### 4-7. 업로드 결과에 어디까지 알려줄 것인가

**행 번호와 사유는 담고, 이름과 휴대폰번호는 담지 않습니다.**

원본 번호를 담으면 마스킹 요구사항을 위반합니다.

### 4-8. CSV 컬럼을 헤더 이름이 아니라 위치로 읽었다

과제 문서가 컬럼 순서가 고정이라는 뜻인지, 이 세 정보가 들어 있다는 뜻인지
명시하지 않았습니다. 헤더 문구가 항상 그 세 단어인지도 알 수 없습니다.

순서가 고정되어 있다고 보고 위치(0, 1, 2)로 읽었습니다. 헤더 이름으로 읽으면
순서 변경에는 강해지지만 헤더 문구가 `연락처`, `휴대폰`으로만 달라져도 파일
전체를 못 읽습니다. 사람이 손으로 만드는 파일에서는 컬럼 순서 변경보다
헤더 문구 변경이 더 흔하다고 봤습니다.

대가로 컬럼 순서가 다른 파일이 오면 전 행이 거절됩니다. 조용히 잘못 저장되는
것이 아니라 전부 거절되니 즉시 알아차릴 수는 있지만, 원인은 알려주지 못합니다.
실제라면 이 CSV가 시스템에서 추출되는 파일인지 담당자가 엑셀로 만드는
파일인지를 먼저 확인해야 합니다.

### 4-9. 마스킹을 어디에 어떻게 적용할 것인가

요구사항은 `010-****-5678` 예시 하나만 줍니다. 

**평문으로 저장하고, 응답 DTO로 변환하는 시점에 가립니다.**
발송에는 원본이 필요하고, 중복 판정도 번호로 하기 때문에 가려서 저장하면
서로 다른 사람이 같은 번호로 취급됩니다. 암호화는 과제 범위를 넘어선다고
판단했습니다.

**프론트가 아니라 서버에서 가립니다.** 프론트에서 가리면 원본이 이미
브라우저까지 내려온 것이라 개발자도구 네트워크 탭에서 평문이 다 보입니다.

### 4-10. 등급 필터의 "전체"를 어떻게 표현할 것인가

등급 파라미터를 보내지 않으면 전체입니다. `Grade` enum에 `ALL` 값을
만들지 않았습니다. `ALL`을 넣으면 등급이 5개가 되어 저장 가능한 값처럼
보이고, DB의 check 제약과 등급 선택 목록에도 섞여 들어갑니다.
"없는 상태"는 별도 값이 아니라 값이 없는 것으로 표현.

없는 등급 값(`grade=VVIP`)이 오면 400으로 응답합니다. 오타를 조용히 무시하고
전체를 보여주면 담당자는 VIP만 필터한 줄 알고 전체 목록을 보게 됩니다.

## 5. 시간이 더 있었다면 개선했을 것 3가지

### 1) CSV 파일 전체를 메모리에 올려 파싱하는 구조

`inputStream.readAllBytes()`로 파일 전체를 문자열로 읽습니다. 40행이면
문제없지만 수십만 행이면 메모리를 다 씁니다. 한 줄씩 흘려 읽으면서 일정
건수마다 저장하는 방식으로 바꿔야 합니다.

그러면 결과 보고 방식도 함께 바뀝니다. 지금은 파싱을 끝낸 뒤 전체 결과를
한 번에 주는데, 스트리밍이면 진행률을 알려주는 비동기 처리가 자연스럽습니다.
관련해서 지금은 파싱까지 `@Transactional` 안에서 하므로 파일을 읽는 동안
DB 커넥션을 붙잡고 있습니다. 대용량이면 파싱을 트랜잭션 밖으로 빼야 합니다.

### 2) 규칙 자체를 검증하는 단위 테스트 (`PhoneNormalizerTest`)
`RecipientCsvParserTest` 는 샘플 파일 하나에 대한 결과를 고정한 테스트입니다.
그래서 샘플에 없는 형태는 아무것도 보장하지 못합니다.

`PhoneNormalizer` 에 파일 없이 값을 직접 던지는 단위 테스트를 두면
이 문제가 해결됩니다. 필요한 케이스는 이렇게 정리했습니다.
- 자릿수 경계값 (9, 10, 11, 12, 13자리)
- 숫자가 아닌 문자가 섞인 값 (`012-abc-1234`)
  — 하이픈만 지우면 10글자가 되어 자릿수 검사를 통과해 버리므로,
  숫자 검사가 자릿수 검사보다 먼저 실행되는지 지켜야 한다
- `null` 과 빈 문자열 — `NullPointerException` 이 아니라
  `InvalidRowException` 으로 거절되어야 한다. 이게 깨지면 파서의
  `catch` 가 잡지 못해서 업로드 전체가 실패한다
- 앞자리 0 누락 시 사유가 자릿수 오류와 구분되는지
- **멱등성** — 이미 정규화된 값을 다시 넣어도 결과가 같은지.
  이게 깨지면 같은 사람을 다른 번호로 판정해서 중복 제거가 무너진다

### 3) `ddl-auto=update`로 스키마를 관리하는 것

개발 편의용 설정입니다. 컬럼 삭제나 타입 변경을 반영하지 않고, 실행 시점에
스키마가 바뀌므로 코드만 봐서는 현재 상태를 알 수 없습니다. Flyway 같은
도구로 변경 이력을 SQL 파일로 관리하는 편이 맞습니다.

### 테스트를 어디에 썼는지

`RecipientCsvParserTest` 하나만 작성했습니다. 제가 구현한 부분은 CSV
파싱에 거의 다 몰려 있고, 4번 항목의 규칙이 전부 이 코드에 있기 때문입니다.
그리고 과제가 "샘플 파일을 그대로 업로드했을 때 동작해야 한다"고 명시했으므로
그 문장은 검증 가능한 인수 조건입니다.

샘플 40행이 저장 32건 / 파일 내 중복 2건 / 거절 6건으로 갈리고 저장분 중
1건에 경고가 남는지, 거절 행 번호가 `29, 32, 33, 34, 39, 40`인지 확인합니다.
`@SpringBootTest`를 붙이지 않았습니다. 검증 대상이 문자열 해석 규칙뿐이라
DB도 스프링도 필요 없어서, MySQL이 꺼져 있어도 1초 안에 끝납니다.

### 그 밖에 알고 있는 문제

- **동시 업로드 경쟁 조건** — 두 요청이 같은 번호를 동시에 저장하려 하면
  DB의 UNIQUE 제약에 걸려 500이 납니다. 데이터는 안전하지만
  "이미 등록된 번호입니다"로 안내하도록 예외를 처리해야 합니다.
- **JPA IDENTITY 전략은 배치 insert가 안 됨** — 대량이면 `JdbcTemplate`으로
  직접 배치 처리하는 편이 훨씬 빠릅니다.
- **`record`의 불변성은 참조까지만** — `CsvParseResult`의 `List`는 내용
  변경이 가능합니다. Java의 record는 필드에 새 값을 재할당하는 건 막아주지만, 필드가 담고 있는 객체 내부까지 못 바꾸게 막아주진 않습니다.
  이 문제를 막으려면 생성자에서 리스트를 그대로 저장하지 않고, 복사본을 만들어 저장하면 됩니다.

## 6. AI 도구 사용 내역

**사용 도구:** Cursor (Claude)

**이 프로젝트의 코드 대부분은 AI가 작성한 초안입니다.**
제가 한 일은 요구사항을 해석해 정책을 정하고, 받은 코드의 동작을
확인하고, 이상한 부분을 되짚어 고치는 것이었습니다.

### 설계 단계 

처음 세 시간은 코드를 쓰지 않고 데이터 정규화 규칙을 새우는데 할애 했습니다. 

기술 선택도 여기서 했습니다. JPA와 MyBatis 중 무엇이 나은지 물었고,
이 과제가 대부분 단순 CRUD이고 "등급 필터 + 페이징"이 요구사항에 있어서
JPA가 유리하다는 답을 듣고 골랐습니다. 

규칙을 정한 뒤 40행에 손으로 적용해서 **32 / 2 / 6 / 1이라는 숫자를 먼저
구하고**, 그다음에 그 값을 테스트 기대값으로 고정했습니다. 코드를 돌려 나온
값을 테스트에 적으면 "현재 동작"을 베끼는 것에 그친다고 봤습니다.

### AI가 알려줘서 알게 된 것

판단은 제가 했지만 문제 자체를 발견하거나 사고 흐름을 배운 경우도 있습니다.
구분해서 적습니다.

- **CSV 파싱을 별도 클래스로 분리한 것은 제 발상이 아닙니다.**
  저는 파일 업로드 API라면 컨트롤러에서 파일을 받고 **서비스 안에서 정규화하고
  걸러내면 된다고 생각했습니다.** 그런데 AI가 준 구조는 클래스가 다섯 개로
  나뉘어 있어서, 왜 이렇게 나눴는지 물었습니다. 두 가지 답을 듣고 채택했습니다.

  하나는 업로드 안에 바뀌는 이유가 다른 일이 섞여 있다는 것입니다. 파일 형식
  해석은 "xlsx도 받아주세요"에 바뀌고, 값 해석 규칙은 "실버 등급 추가요"에
  바뀌고, 저장 정책은 DB 요구에 바뀝니다.

  다른 하나가 결정적이었습니다. 서비스에 다 넣으면 서비스가 리포지토리를,
  리포지토리가 DB를 필요로 해서 **이 로직을 테스트할 수 없습니다.** 그런데
  제가 확인하고 싶은 "40행이 32/2/6/1로 갈리는가"는 DB와 아무 상관이 없는
  순수 계산입니다.

  즉 "무엇을 왜 분리하는가"라는 사고 흐름 자체를 배운 것입니다. 지금은 근거를
  설명할 수 있고 "복잡도가 몰린 곳만 나누고 나머지는 안 나눈다"는 기준도
  이해했지만, 백지에서 제가 떠올렸을 구조는 아닙니다.

- **`"고, 은지"` 때문에 직접 파싱이 불가능하다는 것.** 처음에는 쉼표로 잘라서
  직접 파싱하려고 했습니다. 따옴표 안에 쉼표가 든 이름 하나 때문에
  `split(",")`으로는 이 행이 4개 컬럼으로 쪼개진다는 것을 알고 Commons CSV를
  추천 받았습니다. 

- **검증 순서에 의존관계가 있다는 것.** 숫자 검사가 자릿수 검사보다 먼저여야
  하고, 앞자리 0 검사가 일반 자릿수 검사보다 먼저여야 한다는 것은 설명을 듣고
  알았습니다. 지금은 왜 그 순서인지 말할 수 있습니다.

### 내가 결정한 것

- **샘플의 오염 데이터를 한 줄씩 대조해서 처리 방침을 정했습니다.**
  번호 형식이 하이픈·공백·`+82`·자릿수 오류로 섞여 있고, 등급 표기도
  `VIP`/`vip`/`V.I.P`/`골드`처럼 제각각이며, 이름·번호 누락과 중복 행이
  들어 있었습니다. 어떤 행을 저장하고 버릴지가 정해져 있지 않아서,
  되돌릴 수 없는 발송을 기준으로 규칙을 만들었습니다. 번호는 숫자만
  남긴 뒤 10~11자리·`01` 시작만 통과시키고, 앞자리 0 누락은 추측으로
  복원하지 않고 거절했습니다. 등급은 네 값으로 정규화하되 모르면
  미상으로 살렸고, 이름·번호가 없는 행은 거절했습니다. 중복은 번호
  기준이며 파일 안 중복과 이미 등록된 번호를 나누었습니다.

- 회원 비밀번호처럼 DB에서 암호화로 저장 해야 할까 싶었지만, 비밀번호는 원본을 다시 알아낼 필요가 없고 전화번호는
  원본이 없으면 문자를 못 보낸다는 차이를 확인 하고 DB에는 평문 저장 하였습니다. 

- **유선번호를 `01` 접두어로 거르기로 했습니다.** AI는 통신사 앞자리를
  못 보니 앞자리 검사를 전부 빼 두고, 10자리 유선번호가 통과하는 것을
  막을 수 없다고 적었습니다. 유선은 문자를 받지 못하는데 그게 이상해서
  다시 봤고, `01`로 시작하는지만 보면 샘플 `012`는 살리고 유선은 걸러낸다는
  것을 확인해서 규칙을 바꿨습니다.

- **불필요한 방어 코드를 넣지 않기로 했습니다.** `record`의 `List`는 내용이
  바뀔 수 있다는 설명을 듣고 `List.copyOf`로 막아야 하는지 물었는데,
  수정 경로가 없다는 것을 확인하고 넣지 않았습니다.

- **기능 범위를 줄이는 결정을 했습니다.** 발송·이력을 추가하면 파일이 7개 이상
  늘어나는데 그 시점에 이미 기존 코드를 따라가지 못하고 있었습니다.
  자세한 사정은 8번에 적었습니다.

- **버그를 화면에서 찾았습니다.** 같은 파일을 두 번 올렸을 때 "저장 0건"인데
  "미상으로 저장했습니다" 경고가 남는 것을 발견했습니다. 경고는 파서가 만들고
  "이미 등록된 번호" 판정은 그 뒤에 서비스가 하기 때문이었습니다. 고친 뒤에도
  증상이 그대로여서 다시 보니, 걸러낸 목록을 변수로 만들어 두고 응답에는 원래
  목록을 넘기고 있었습니다. 두 값의 타입이 같아서 컴파일 에러가 나지 않는
  실수였습니다.

### 이해도가 어디까지인지

**설명할 수 있는 것.** 4번 항목의 판단들은 근거를 갖고 결정했으므로 설명할 수
있습니다. 번호를 숫자만 남겨 저장하는 이유, 앞자리 0을 복원하지 않은 이유,
통신사 앞자리 목록까지 좁히지 않고 `01` 접두어만 검사한 이유, 거절과 경고를
나눈 기준, 두 종류의 중복을 구분한 이유, 마스킹을 서버에서 하는 이유등 입니다.

**약한 것.**

- CSV 파서의 **전체 구조는 제가 설계한 것이 아닙니다.** 규칙의 순서와 행마다
  `try-catch`를 두어 부분 저장이 되게 한 이유는 설명할 수 있지만, 이 구조를
  백지에서 떠올렸을지는 자신하지 못합니다.
- Spring Data JPA가 메서드 이름만으로 쿼리를 만드는 원리는 "이렇게 쓰면 이런
  SQL이 나간다"는 수준까지만 알고, 내부에서 프록시를 만드는 과정은 모릅니다.
- `@Transactional`이 프록시 기반이라는 사실만 알고, 같은 클래스 안에서
  호출하면 적용되지 않는다는 등의 세부는 직접 확인해 보지 못했습니다.
- `@ElementCollection`, `@JdbcTypeCode` 같은 어노테이션은 개념만 봤고
  실제로 써보지는 않았습니다.

## 7. 미완성 항목

### 어디까지 했고 어디서 멈췄는지

| 요구사항 | 상태 |
|---|---|
| 1. 수신자 목록 업로드 | 완료 |
| 2. 수신자 목록 조회 (등급 필터 + 페이징) | 완료 |
| 3. 메시지 발송 요청 | **미구현** |
| 4. 발송 이력 조회 | **미구현** |
| 5. 개인정보 마스킹 | 완료 |

발송과 이력은 테이블 설계만 해두고 코드는 작성하지 않았습니다.

### 왜 그 지점에서 멈췄는지

**시간이 없었습니다.** 월~금, 토일 전부 알바라서 저녁·주말에 손을 댈 여유가 거의 없었습니다.

**처음 요구사항을 봤을 때 발송이 막막했습니다.** 개인 휴대폰으로 문자를 어떻게 보내는지 이론이 머리에 안 떠올랐고, 기술적으로도 바로 방법이 안 보였습니다. 그걸 리서치하고 정리해서 설계할 겨를이 없었습니다.

그래서 당장 손이 가는 업로드·조회부터 했고, 그 후에는 구현 시간이 없었습니다.

### 돌아보면

설계 단계는 순서가 맞았습니다. 코드를 받기 전에 정책을 다 정했고, 기대 결과를
손으로 먼저 계산했습니다. 문제는 그다음이었습니다. 구현에 들어가면서 **코드를 받아
읽어야 하는 양이 이해하는 속도를 앞질렀고**, "동작한다"는 확인에 만족하고 넘어간
파일이 생겼습니다. 중간에 그 사실을 깨닫고 기능을 늘리는 것을 멈췄습니다.

다시 한다면 파일 하나를 받을 때마다 직접 다시 써보면서 진행했을 것입니다.
`PhoneMasker`처럼 규칙만 알면 제가 쓸 수 있는 3줄짜리 클래스도 받아서
붙여넣은 것이 지금 가장 아쉽습니다.

과제에 "이해가 안 된 채로 들어간 부분이 있다면 솔직하게 적어달라"고 되어
있어서 그대로 적었습니다.
